# PokeTokenLite

Claude Code 토큰 사용량으로 포켓몬(1~6세대, 721마리)을 키우는 개인용 Windows
트레이 앱 MVP.

## 현재 상태: 동작 확인됨

부화 → 진화 → 졸업, 도감(721마리 전체 표시·미발견은 실루엣, 1~6세대 전부
처음부터 후보, 행 펼치면 타입/설명까지), 보관함(성장 중 교체), 알 보관함(등급별
부화 + 매주 무료 티켓), 상점(이상한 사탕/이로치 부적/등급 보장 알을 토큰으로
구매) + 가방(사탕 보관 후 사용), 이로치, 애니메이션 스프라이트, 항상 떠있는
위젯, 설정 화면(새로고침 주기/부화 가중치/난이도 배율/알림/자동 실행)까지 Windows
실기에서 직접 확인 완료. Windows
알림·시작 시 자동 실행은 코드는 붙였는데, 실제 동작(토스트/로그인 자동실행)은
아직 Windows 실기 확인 전(WSL/Linux는 Electron이 이 두 API를 지원 안 함).
`npm run dist`로 포터블 exe 빌드도 가능.

## 실행 순서

```bash
npm install
npm run build-data     # PokéAPI에서 1~6세대 721마리 데이터 fetch (인터넷 필요, 1회만, 좀 걸림)
npm start               # Electron 앱 실행 (개발용)
npm run dist            # 포터블 exe 빌드 (dist/ 폴더에 생성, 설치 없이 실행 가능)
```

## 구조

```
src/
  logParser.js   Claude Code JSONL 로그 읽어서 누적 토큰 계산 (WSL 로그 경로도 자동 탐색)
  growth.js      등급별(common/uncommon/epic/legendary/mythical) 임계치로 부화/진화/졸업 판정
  shop.js        상점 가격/효과량 상수(이상한 사탕/이로치 부적/등급 알)
  state.js       컴패니언/도감/보관함/알 보관함/상점 재화·가방을 로컬 JSON에 저장
  main.js        Electron 메인 프로세스, 트레이 아이콘, IPC, 폴링
scripts/
  build-pokedex-data.js   PokéAPI → data/pokedex.json 빌드 스크립트(세대별 독립 범위)
renderer/
  popup.html     트레이 클릭 시 뜨는 팝업 (컴패니언/도감/보관함/알보관함 탭)
  widget.html    항상 떠있는 미니 위젯
  preload.js     contextBridge로 렌더러에 안전하게 IPC 노출
```

## 2~6세대 추가 — 완료

도감 등록 구조(졸업한 라인 전체 영구 등록 + 성장 중/보관함 진행분 실시간 발견)는
이전에 먼저 해결해서 151/151이 구조적으로 달성 가능해져 있었고, 실제 2세대
데이터를 붙였다.

**세대별 독립 범위 빌드**: PokéAPI의 evolution-chain은 세대 구분이 없어서(예:
이브이(1세대)의 진화형이 2·4·6세대에 걸쳐있음) 직접 확인 후 `flattenChain()`을
`(minId, maxId)` 범위를 받게 일반화해서, **1세대(1~151)와 2세대(152~251)를
서로 완전히 독립된 범위로 각각 클리핑**해 빌드한다(`scripts/build-pokedex-data.js`).
그래서 폴리곤(1세대)→폴리곤2(2세대)처럼 세대를 넘나드는 진화는 각 세대 파일에서
독립된 별개의 종으로 취급됨(폴짝몬(2세대 베이비)→얼음귀신(1세대) 같은 반대
방향도 동일 — 1세대 데이터의 피츄→피카츄 관계가 이미 이렇게 끊겨있던 것과
같은 패턴). 결과는 `data/pokedex.json` 하나에 1~251 전부, 각 항목에
`generation: 1|2` 필드로 구분(지금은 게임 로직에서 이 필드를 안 씀 — 아래 참고).

**해금 조건 → 폐기, 처음부터 전체 오픈으로 변경(사용자 확정)**: 처음엔 "1세대
151/151 채우면 2세대 해금" 단계적 잠금으로 구현했었는데, 레퍼런스(PokeTokenBar)
소스를 직접 확인해보니 그런 단계적 잠금이 아예 없었다 — `PokemonAssets
.animatedSpeciesIDs = 1...649`(1~5세대 전체)를 **처음부터 하나의 풀로** 써서
capture_rate 가중치로만 자연스럽게 희귀도를 조절함. 우리도 이 방식으로 맞춰서
`state.unlockedGen`/`checkGenUnlock()`/부화 풀의 `maxGen` 필터를 전부 제거 —
**전체 종이 처음부터 다 부화 후보**. 도감 분모(`pokedexTotal`)도 `gen1Data`
크기(=`data/pokedex.json`에 들어있는 종 수)를 그대로 쓰기 때문에 세대가
늘어나도 항상 자동으로 맞음. (판단 근거: 1세대 151/151엔 전설·환상까지
포함되는데, 그거 다 채울 때까지 2세대를 아예 구경도 못 하는 게 캐주얼한
개인용 앱치고 너무 늦게 열린다고 판단해서 레퍼런스 방식으로 되돌림.)

**3세대(호연, 252~386) 추가**: 위 두 가지(세대별 독립 범위 클리핑, 해금 없는
전체 오픈)가 이미 세대 수와 무관하게 일반화돼 있어서, `GENERATIONS` 배열에
`{ gen: 3, min: 252, max: 386 }` 한 줄만 추가하고 재빌드하는 것으로 끝났다 —
게임 로직(`growth.js`/`main.js`) 쪽은 전혀 안 건드림. 크로스세대 진화 클리핑도
그대로 잘 작동함을 확인(예: 루리리(3세대 #298)→마릴(2세대 #183)은 2세대
피츄→피카츄 케이스와 똑같이 루리리가 독립된 1단 종으로 분리됨). 레쿠쟈(전설),
지라치·테오키스(환상) 등급도 `is_legendary`/`is_mythical` 플래그로 정상 분류
확인.

**4세대(신오, 387~493) 추가 — 그리고 "샌드위치 체인" 버그 발견/수정**: 배열에
`{ gen: 4, min: 387, max: 493 }` 한 줄 추가하고 재빌드하는 것까진 3세대 때와
동일했는데, 빌드 결과를 스팟체크하다가 새로운 종류의 버그를 하나 발견했다 —
꼬몽울(4세대 #406)→로젤리아(3세대 #315)→로즈레이드(4세대 #407)처럼 **양 끝은
같은 세대인데 중간만 다른 세대인 "샌드위치" 체인**에서, 4세대 빌드가 로젤리아를
건너뛰면서도 그 이후 노드(로즈레이드)에 "범위 안 조상까지의 단계 수"를 그대로
물려주는 바람에 로즈레이드가 stage:2로, 같은 체인 캐시를 공유하는 꼬몽울의
maxStage까지 2로 잘못 올라가는 문제였다. 근데 evolvesTo 엣지는 원본 트리에서
직접 인접한 노드끼리만 잇기 때문에(중간에 범위 밖 노드가 끼면 간접 연결 안 함)
꼬몽울→로즈레이드 엣지는 끝내 안 생겨서, 꼬몽울이 "2단계인데 다음 단계로 갈
evolvesTo가 없는" 모순 상태가 됐다 — 실제로 키우면 `evaluate()`가 다음 종을
못 찾아 자기 자신으로 폴백해서, 겉보기엔 진화/졸업 이벤트가 뜨는데 스프라이트는
안 바뀌는 버그로 이어졌을 것. 493종 전체를 "stage < maxStage인데 evolvesTo가
비어있는" 조건으로 스캔해서 이 패턴에 해당하는 게 꼬몽울 하나뿐임을 확인하고,
`flattenChain()`이 범위 밖 노드를 지날 때 `relativeStage`를 이어받지 않고
무조건 `undefined`로 리셋하도록 한 줄 고쳤다 — 이러면 꼬몽울·로즈레이드가
루리리→마릴처럼 완전히 독립된 1단(stage:1, maxStage:1) 종으로 정직하게
분리된다. 이미 검증된 2단 크로스세대 케이스(피츄→피카츄, 루리리→마릴)는
애초에 범위 밖 노드를 한 번만 거치는 구조라 이 수정으로 동작이 안 바뀌는 것도
재확인(재빌드 후 493종 전체 재스캔으로 회귀 없음 확인). 메가진화 39종·
기가맥스 12종(아래 "부스트" 기믹 백로그 참고)은 4세대 추가 후에도 그대로 —
예측대로 4세대엔 공식 메가진화가 하나도 없었다.

`gen1Data`라는 변수/전역명은 그대로 유지(20곳 넘게 쓰여서 순수 리네이밍 값어치가
없음) — 이제 1~6세대 다 담겨있다는 점만 로딩 부분 주석으로 남겨둠.

**5세대(하나, 494~649)·6세대(칼로스, 650~721) 추가**: 둘 다 배열에 한 줄
추가+재빌드, 전체 stage/maxStage/evolvesTo 일관성 스윕(4세대 때 만든
"샌드위치 체인" 체크 포함) 통과, 특이사항 없음.

## 상점 + 가방 — 완료

백로그 "알 구매/퀘스트/보상 시스템"을 레퍼런스(PokeTokenBar) `ShopView.swift`/
`CompanionStore.swift`로 직접 확인해보니 **퀘스트는 레퍼런스에 없어서**(관련
파일 자체가 없음) "상점"으로 스코프를 좁혔다. 민트(성격 리롤)는 우리가 성격
시스템 자체가 없어서 스킵.

재화(`spendableTokens` = 누적 토큰 − `state.tokensSpent`)는 성장 진행도
(`hatchedAtTotal` 기준 실시간 파생값)와 완전히 독립 — 상점에서 아무리 사도
지금 키우는 개체의 진화 속도엔 영향이 없다(레퍼런스 `availableTokens =
usedSinceInstall - spentTokens`와 동일 원칙). 이 앱은 저장된 XP 누적치가
없고 진행도를 항상 `totalTokens - hatchedAtTotal`로 실시간 계산하기 때문에,
이상한 사탕의 "XP를 더한다" 효과는 곧 `hatchedAtTotal`(알이면 `eggStartTotal`)을
과거로 당기는 것과 동치다(`resumeStoredCompanion()`의 `frozenProgress` 역산과
같은 패턴 — `growth.js`의 `applyRareCandy()`).

판매 아이템: 이상한 사탕(가방에 보관 후 사용 — 사용 시 진행도 즉시 +500만,
`HATCH_THRESHOLD`와 동급), 이로치 부적(1회성, 보유하면 이로치 확률 영구 2배),
등급 보장 알(가격은 `GRADUATION_TOTAL[tier]`의 20% — 레퍼런스는 구매 즉시
현재 개체를 폐기+교체하지만, 우리는 기존 "알 보관함 → 품기 시작" 경로가 더
단순하고 일관적이라 그대로 재사용).

## 다음 단계 (우선순위 낮음)

- **메가진화/기가맥스/테라스탈 같은 "부스트" 기믹 (이름 미정)** — 레퍼런스
  (PokeTokenBar)엔 없는 기믹, 본가 게임 컨셉에서 따온 사용자 아이디어라
  검증된 설계는 아니고 구상 단계 메모. 기본 규칙(사용자 확정):
  - 지금 키우는 컴패니언을 토글로 "부스팅 상태"로 전환.
  - **부스팅 중엔 토큰이 평소 진화 진행도(`hatchedAtTotal` 기준)로 안 가고,
    대신 별도의 부스트 게이지로 감** — 즉 부스팅 켜져있는 동안은 진화가
    멈추고 그 대신 게이지가 채워짐(토글 꺼져있을 때만 평소처럼 진화 진행).
  - 부스트 게이지를 다 채우면 보상 지급.
  - 구현 시 참고: 진행도를 저장된 XP가 아니라 `totalTokens - hatchedAtTotal`
    로 실시간 파생 계산하는 현재 구조상, "부스팅 중 진화 멈춤"은 부스팅
    동안 `hatchedAtTotal`도 토큰 증가분만큼 같이 밀어서 진행도를 그대로
    고정시켜두는 방식으로 구현 가능(상점의 `applyRareCandy()`가 반대
    방향으로 당기는 것과 같은 계열 트릭).

  **어떤 종이 어떤 기믹을 쓸 수 있는지 — PokéAPI로 실측 확인(1~721,
  1~6세대 기준. 4~6세대 추가 후 재확인 — 메가진화/기가맥스 수는 그대로였음,
  아래 참고).** 메가진화/기가맥스는 본가에서도 정해진 종만 가능한
  제한적 기믹이라 종 목록이 필요함(테라스탈은 본가에서 종 제한이 없어서
  목록 불필요 — 아무 종이나 가능). PokéAPI에 `mega-dimension`이라는
  버전그룹으로 라이츄/클레피/우츠보트/시드라/망나뇽 등 **공식 게임에 없는
  팬메이드 메가진화 폼도 섞여 들어있어서**, `version_group`이 실제 공식
  게임(`x-y`/`omega-ruby-alpha-sapphire`, 기가맥스는 `sword-shield`)인
  것만 걸러냈다:
  - **메가진화 가능 39종** (전부 1~3세대 안에 이미 있음, 4세대(387~493)엔
    신규 메가진화가 하나도 없어서 4세대 추가 후에도 그대로 39종 — 공식 메가진화는
    6세대(ORAS)까지만 나오고 이후 세대엔 아예 없어서, 나중에 4세대 이상을
    추가해도 이 목록은 더 안 늘어남): 이상해꽃·리자몽·거북왕·독침붕·피죤투·
    후딘·야도란·팬텀·캥카·쁘사이저·갸라도스·프테라·뮤츠·전룡·강철톤·핫삼·
    헤라크로스·헬가·마기라스·나무킹·번치코·대짱이·가디안·깜까미·입치트·
    보스로라·요가램·썬더볼트·샤크니아·폭타·파비코리·다크펫·앱솔·얼음귀신·
    보만다·메타그로스·라티아스·라티오스·레쿠쟈.
  - **기가맥스 가능 12종** (지금 데이터 안에 있는 것만 — 갈라르 도감 기준
    나머지 기가맥스 종은 8세대(가라르, 810~905) 추가해야 나옴): 이상해꽃·
    리자몽·거북왕·버터플·피카츄·나옹·괴력몬·팬텀·킹크랩·라프라스·이브이·
    잠만보.
  - **테라스탈**: 종 제한 없음 — 지금 있는 721종 전부(나중에 더 늘어나도
    마찬가지) 적용 가능.

  **보상 종류 — 사용자 제안(사탕/알/상점 재화) + 추가 아이디어(전부 미정,
  나중에 하나 골라서 결정):**
  1. 사탕/알/상점 재화 지급 (사용자 원안) — 구현은 제일 간단하지만, 상점에서
     이미 살 수 있는 거라 "왜 굳이 진화를 멈추면서까지" 하는 동기가 약할 수
     있음(배율/양을 상점보다 확실히 유리하게 주지 않으면).
  2. **(추가 아이디어) 진행도 캐치업 + 보너스** — 게이지를 다 채우면 부스팅
     동안 멈춰있던 진행도를 보너스 배율(예: 1.2~1.5배)까지 얹어서 한 번에
     돌려줌. "부스팅 리스크(그동안 진화 멈춤)를 감수한 대가"라는 이 기믹만의
     정체성이 생기고, 상점 사탕(즉시 소모)이랑 성격이 겹치지 않음.
  3. **(추가 아이디어) 코스메틱 뱃지** — 그 라인이 나중에 졸업(도감 등록)할
     때, 부스트 게이지를 채운 이력이 있으면 도감 항목에 "메가/기가맥스/
     테라스탈 경험" 뱃지가 영구히 붙음. 밸런스에 전혀 영향 없는 순수 수집
     요소라 상점 보상이랑 절대 안 겹침 — 2번(진행도 보너스)이랑 같이 써도 됨.
  4. 추가로 고민할 지점(아직 미정): 부스팅 껐을 때 게이지 진행분이 유지되는지
     리셋되는지, 부스팅 중 시각 연출(스프라이트 색조/이펙트 등) 넣을지,
     반복 사용 가능 여부·쿨다운 유무.
- **7~9세대 추가** — 2~6세대 때 이미 세대 수 무관하게 일반화해둔 구조라
  `scripts/build-pokedex-data.js`의 `GENERATIONS` 배열에 한 줄씩만 추가하고
  재빌드하면 되는 기계적인 작업(게임 로직은 안 건드림, 4세대 추가 때 발견한
  "샌드위치 체인" 버그도 이미 고쳐져 있어서 그 패턴 걱정 없이 진행 가능).
  PokéAPI로 실측 확인한 정확한 범위(전부 빈틈없이 연속):
  - 7세대(알로라): `{ gen: 7, min: 722, max: 809 }` (88마리)
  - 8세대(가라르): `{ gen: 8, min: 810, max: 905 }` (96마리) — 기가맥스
    나머지 종(갈라르 네이티브)이 이때 추가됨, "부스트" 기믹 백로그의 기가맥스
    목록 재확인 필요.
  - 9세대(팔데아): `{ gen: 9, min: 906, max: 1025 }` (120마리)
  - 다 더하면 1025마리. 한 번에 다 넣기보다 세대별로 나눠서 재빌드(빌드 시간
    분산 + 크로스세대 진화 클리핑 세대마다 스팟체크하기 쉬움) 추천 — 특히
    "양 끝은 이미 있는 세대, 중간만 새 세대"인 샌드위치 케이스가 생길 수
    있는 세대는 재빌드 후 전체 종 스캔에서 썼던 "stage < maxStage인데
    evolvesTo 비어있음" 체크를 다시 돌려보는 게 안전함.
- **5시간/주간 한도 도달 시 "이상한 사탕" 보상 — 보류.** 한도 정보(`/status`에
  뜨는 세션/주간 % 게이지)가 로컬에 저장 안 되고 서버 쪽에서만 계산되는 값이라
  실제로 확인함(비공식 API로 흉내 내려면 OAuth 토큰을 가져다 써야 해서 그때
  안 하기로 함) — 로컬 로그만으로는 "한도 도달"을 감지할 방법이 없어서 착수
  자체가 막혀있음. 나중에 감지 방법이 생기거나(공식 API 등), 순수 토큰
  총량 임의 기준으로 근사하는 걸로 타협하면 재검토.
- Codex/Gemini 탭 실제 구현 (지금은 팝업에 탭만 있고 "다음 라운드 예정" 플레이스홀더)
- **Electron → 네이티브 전환 검토** — Tauri(Rust, popup.html 거의 그대로 재사용

## 튜닝 포인트

`src/growth.js`:
- `HATCH_THRESHOLD` (알 → 부화까지 필요 토큰, 500만 — 안 건드림)
- `GRADUATION_TOTAL` (등급별 졸업까지 총 토큰) — 레퍼런스(PokeTokenBar) 실측값
  (레퍼런스 "실측 평균 하루 2.53억 토큰" 기준)의 **정확히 1/5**로 축소해서 씀.
  처음엔 이 프로젝트 실측 사용 패턴(평일 활동일 평균 약 8,150만 토큰/일,
  2026-09-08~09-14 기준)으로 "에픽 = 평일 1주일"이 되게 1/7.5까지 낮췄었는데
  너무 빠르다는 피드백으로 1/5(에픽 = 대략 1.5~3주, 활동 페이스에 따라 다름)로
  다시 올림. 등급 간 비율(common:uncommon:epic:legendary:mythical =
  0.25:0.625:1:2:4)은 그대로 유지 — **common 1.5억 / uncommon 3.75억 /
  epic 6억 / legendary 12억 / mythical 24억**. 이 표 자체는 "배율 1.0 기준값"
  으로 고정해두고, 실제 페이스 조절은 이제 코드 수정 없이 **설정 화면의
  난이도 슬라이더(0.1~2.0)** 로 함 — `stageThresholds()`/`HATCH_THRESHOLD`
  둘 다 소비 지점에서 이 배율을 곱함(레퍼런스 `PokemonBalance.scaled()`와
  동일 원칙 — 상수표 자체를 건드리면 다른 파생값까지 같이 끌려가서).
- `TIER_RANK` (등급 알의 "이 등급 이상 보장" 판정용 순위)
- `WEEKLY_TICKET_GRADE_WEIGHTS` (매주 월요일 10시 무료 알 티켓의 등급 가중치 —
  직접 정한 값, common 55 > uncommon 25 > epic 12 > legendary 6 > mythical 2)

`scripts/build-pokedex-data.js`의 `TIER_BOUNDS` — capture_rate 기준 희귀도
경계값(epic≤45, uncommon≤120, 그 이상 common). 전설/환상은 capture_rate가
아니라 PokéAPI `is_legendary`/`is_mythical` 플래그로 판정.

`src/shop.js` (상점 가격/효과량 — growth.js 상수를 참조만 하고 growth.js는
이 파일을 모름, 단방향 의존성):
- `RARE_CANDY_XP`/`RARE_CANDY_PRICE` (이상한 사탕 효과량/가격, 둘 다
  `HATCH_THRESHOLD`와 동급인 500만 — 1:1, "지금 당겨쓰기"의 대가)
- `SHINY_CHARM_PRICE`/`SHINY_CHARM_DENOMINATOR` (이로치 부적 가격 = epic
  졸업 총량과 동급인 고가 럭셔리 아이템, 분모는 `SHINY_DENOMINATOR`의 절반 =
  확률 2배)
- `EGG_PRICE_RATIO` (등급 보장 알 가격 = 그 등급 `GRADUATION_TOTAL`의 20%)
